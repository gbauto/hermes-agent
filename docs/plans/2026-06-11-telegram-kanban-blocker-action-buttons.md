# Telegram Kanban blocker action-button contract

Status: patch plan / design note for `gbauto/hermes-agent`.

Source report: `/Users/greg/repos/gbautomation/second-brain/intelligence/integration-experts/t_ee9bd5a1-observability-control-plane-contracts.md`, Contract 1 and Contract 2.

## Goals

- Keep the Kanban SQLite DB as the source of truth for task lifecycle, comments, block reasons, terminal events, and notify subscription cursors.
- Add Telegram inline action buttons only as a thin control-plane affordance on top of `task_events` and existing Kanban DB operations.
- Make every callback payload opaque, signed, and short enough for Telegram's 64-byte `callback_data` limit.
- Fail closed for unauthorized callback users.
- Never encode raw task metadata, secrets, OAuth material, service keys, transcripts, or task payload blobs into Telegram callback data.

## Non-goals

- Do not make Telegram the authority for task state.
- Do not add ad-hoc blocker chat messages outside the `blocked` event flow.
- Do not mirror full task/run payloads into Telegram callback data.
- Do not make callbacks rely on private transcripts or Supabase mirrors.

## Current gap in `gbauto/hermes-agent`

`gateway/kanban_watchers.py::_kanban_blocker_keyboard_metadata` currently emits legacy prototype callback data shaped like `kbp:<action>:<board>:<task_id>`. That shape is intentionally not the contract: it exposes board/task routing material in Telegram callback data and should be treated as a migration target, not a durable API.

The patch plan below replaces that helper with an opaque, signed short-ID flow before the blocker buttons are considered production-safe.

## Proposed callback payload shape

Use a compact envelope:

```text
kb:<action>:<sid>:<sig>
```

Fields:

- `kb`: namespace for Kanban Telegram callbacks.
- `<action>`: a short verb, e.g. `ub` for unblock, `ack` for acknowledge, `open` for deep-link/details.
- `<sid>`: opaque short ID generated by Hermes and persisted server-side.
- `<sig>`: truncated HMAC over `kb:<action>:<sid>` using a gateway-local signing key.

Example:

```text
kb:ub:k7Fa2qPz:d8CqTA
```

The full string stays below Telegram's 64-byte cap. It contains no task ID, board slug, assignee, reason, metadata, credentials, token material, or transcript text.

## Server-side state

Persist callback state in the Kanban DB, not process memory, so gateway restarts do not strand buttons.

Suggested additive table:

```sql
CREATE TABLE IF NOT EXISTS kanban_callback_actions (
    sid          TEXT PRIMARY KEY,
    task_id      TEXT NOT NULL,
    board        TEXT,
    action       TEXT NOT NULL,
    platform     TEXT NOT NULL,
    chat_id      TEXT NOT NULL,
    thread_id    TEXT NOT NULL DEFAULT '',
    user_id      TEXT,
    event_id     INTEGER,
    created_at   INTEGER NOT NULL,
    expires_at   INTEGER NOT NULL,
    used_at      INTEGER,
    used_by      TEXT
);
CREATE INDEX IF NOT EXISTS idx_kanban_callback_task ON kanban_callback_actions(task_id);
CREATE INDEX IF NOT EXISTS idx_kanban_callback_expiry ON kanban_callback_actions(expires_at);
```

The table stores lookup data needed to perform the action. The Telegram payload only carries `sid` plus signature.

## Button creation flow

1. `gateway/run.py::_kanban_notifier_watcher` receives a `blocked` task event from `task_events`.
2. It renders the Contract 2 text first: status, assignee, task ID, short reason.
3. If the delivery platform is Telegram, it asks the Telegram adapter to send a Kanban notification with optional buttons.
4. The adapter or shared helper creates a `kanban_callback_actions` row for each button and signs the short payload.
5. It sends inline buttons such as:
   - `✅ Unblock` -> `kb:ub:<sid>:<sig>`
   - `📝 Comment` or `Open task` can be added later only if they route through existing safe `/kanban` or DB operations.
6. Cursor handling remains unchanged: failed sends rewind the subscription cursor; success advances only after delivery.

## Callback handling flow

1. `gateway/platforms/telegram.py::_handle_callback_query` dispatches `kb:` callbacks.
2. Verify payload parse, allowed action, short-ID existence, expiry, unused status, and HMAC signature before doing anything else.
3. Authorize the Telegram user with `_is_callback_user_authorized(...)`; deny on missing allowlist/runner auth just like approval, slash-confirm, clarify, and update callbacks.
4. Re-open the Kanban DB for the stored board and reload the task by `task_id`.
5. Re-check current state from DB:
   - `ub`: task must still be `blocked`; call `kanban_db.unblock_task(conn, task_id)`.
   - If the task is already unblocked/done/archived, answer with a no-op status and do not mutate.
6. Mark the callback row used in the same transaction as the Kanban mutation where practical.
7. Let `unblock_task` append the `unblocked` event; do not synthesize state from Telegram.
8. Edit the Telegram message only as cosmetic UI feedback. The DB event remains authoritative.

## Security rules

- Payloads are opaque and signed; raw task IDs and board paths do not appear in `callback_data`.
- Payloads do not include secrets, OAuth material, service keys, metadata blobs, artifact paths, or private transcript excerpts.
- Unknown namespaces/actions/signatures/expired IDs answer with a generic invalid/expired message and perform no mutation.
- Unauthorized users answer with `⛔ You are not authorized to act on this Kanban task.` and perform no mutation.
- Callback state expires; cleanup can piggyback on Kanban GC.
- Board/task state is always re-read at click time to prevent stale button mutations.

## Test plan

Add tests under `tests/gateway/` for:

- Payload helper returns a string under 64 bytes and omits raw task IDs/metadata.
- Bad signature, unknown `sid`, expired row, and already-used row fail closed without calling `unblock_task`.
- Unauthorized Telegram users fail closed before any Kanban DB mutation.
- Authorized `kb:ub` callback unblocks only a currently blocked task and emits the normal `unblocked` event.
- Send failure keeps existing notifier rewind behavior unchanged.
